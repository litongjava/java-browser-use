# 登录页白屏问题与版本对照（2026-09-22）

> 当前处理：按用户要求回退到 Playwright 1.53.0，并恢复匹配的 Chromium 1179 打包配置。遇到类似白屏时可尝试 Playwright 1.53.0 + Firefox 139.0。下文的 1.63 升级、发行包和测试结果保留为历史诊断记录，不代表当前依赖版本。

此次证据直接说明登录端点的 HTTP 错误之后页面没有内容，不能据此确认服务器返回 400 的具体规则，也不能统一归因于沙盒或此前发现的 disable-devtool 跳转。之前 Playwright 1.53 + Firefox 139 的一次测试成功显示表单；本次新版 Firefox 失败，浏览器版本、测试时间和站点验证状态均有变化，不能单凭这两个结果认定版本回归。

## Edge 修复

系统安装目录中的主程序叫 `Microsoft Edge.exe`，缺少 Playwright 查找的 `msedge.exe`。原文件 Microsoft 数字签名有效。直接使用这个改名路径启动时进程立即关闭；系统安装目录不允许当前进程写入。

已将版本目录及签名有效的主程序复制到当前用户目录，并使用标准文件名：

`C:\Users\Administrator\AppData\Local\Microsoft\Edge\Application\msedge.exe`

Playwright 的 `msedge` 通道随后正常启动并完成全部测试。此修复恢复了当前用户的 Playwright Edge 启动，没有覆盖系统安装或用户浏览数据，也没有升级 Edge 本身。

- Windows 发行包构建成功；成品 jar 实测 Playwright 1.63.0 + 内嵌浏览器 153.0.8010.12，页面标题读取和输入操作通过。包内资源检查通过，不含旧版浏览器目录或其他平台的 Node。
- 广泛测试中，用户 profile/CDP 测试期望 `cdp`，实际回退为 `managed`。使用 1.53 重新编译并单独运行也出现同样失败，因此不是本次升级新增的失败。外部百度/淘宝测试最初因新版浏览器尚未安装失败，未计入上述 49 项验证。
- 后续（2026-09-23）：上面这条已定位并修掉。根因不在 Playwright 版本，而在 `ChromeBrowser.profileInUse()`：它把「进程命令行读不到」当成「profile 被占用」，而这台机器上以管理员身份运行时 `ProcessHandle` 读不到**任何** Chrome 进程的命令行（连本进程自己拉起的子进程也读不到），于是任何目录——包括测试刚建的临时目录——都被判成「Chrome 正在运行」，CDP 那条路永远走不到。现在改成只认实证（命令行里确实提到该目录，或类 Unix 上的 `SingletonLock` 指向一个活着的 PID），没有实证就真的去试一次 CDP：profile 真被占着时新进程会立即退出，`ChromeLauncher` 能从「进程已退出」立刻判断并退回托管 profile，不必等超时。`ChromeCdpModeTest` 由此恢复通过。

新版独立发行包：`dist/deepseek-browser-use-1.0.0-windows-x64-playwright-1.63.0.jar`。旧名称的发行包保留，现有服务没有自动切换。
